Examples

These examples follow one shop domain from start to finish. The snippets come from the runnable tour in examples/Plasm.Examples, and the outputs shown are what it printed against PostgreSQL.

Plasm has one way to build an application. The records it stores are your domain's own records. A record owns lists and records, and links to shared ones; Plasm always reads them and writes them with it. Other aggregates are referred to by id. Queries are plasm { } values. Every write is a typed transaction. Plasm doesn't validate input: your domain's constructors and functions do that.

Each example can switch to the SQL Plasm generated for it, with the parts that make that example different highlighted. The SQL is captured from the library's diagnostics while the examples run, not written by hand.

Run the tour

The tour provisions a throwaway PostgreSQL database with Testcontainers and creates its tables from the DDL Plasm prints for the model. To use a server you already have, set PLASM_TEST_PG to an admin connection string.

dotnet run --project examples/Plasm.Examples

1 · The model

The domain is plain immutable records. A stored record names its table with [<Table>], and its key is its field named Id. Everything else follows from the types. An integer key, or a typed id over one such as OrderId, is generated by the database; any other key is assigned by the application. A list, record or option field whose records hold the owner's key is owned: an order's lines hold its OrderId, so they are read and written with it, in the order of their key. The customer is another aggregate, so the order holds only its id. A column is named after its field, in snake_case.

[<Table "customers">]
type Customer =
    { Id: CustomerId
      Name: string
      [<Unique>]
      Email: string }

/// An order owns its lines, which hold its key: they are read with it, in the
/// order of their key, and written with it. Its customer and its payments are
/// other aggregates, referred to by id.
[<Table "orders">]
type Order =
    { Id: OrderId
      CustomerId: CustomerId option
      Status: OrderStatus
      Total: decimal
      PlacedAt: DateTime
      [<Version>]
      Version: int
      Lines: OrderLine list }

and [<Table "order_lines">] OrderLine =
    { Id: OrderLineId
      OrderId: OrderId
      ProductId: ProductId
      Quantity: Quantity
      UnitPrice: decimal }

module Db =
    let all = [ typeof<Customer>; typeof<Product>; typeof<Order>; typeof<Payment>; typeof<Article>; typeof<Tag> ]

    /// Checked once at start-up; every problem is reported with model and field.
    let model = Model.buildOrFail [] all

let! orders = repo.All(Query.from (tableOf<Order>))   // every Order with its Lines

The model lists only the records that are not owned; an order's lines come with it. What no type can say is an attribute on the field: [<Unique>] (here customers_email_key), [<Version>] for optimistic concurrency, [<Generated>] for a value the database fills, [<Assigned>] for an integer key the application chooses, [<NotReference>] for a typed id that refers to nothing, and [<OrderedBy>] to read an owned list in another order. A record can also own one record, or one that may be absent, as a record or option field. Anything the types leave ambiguous, such as a list item holding its owner's key twice, is refused when the model is built.

2 · Scalars by convention

The model above registers no mappings: the types say how they are stored. A single-case union over a built-in type, such as OrderId, is stored as that type. A type with a create function is always read through it, so a stored zero quantity is a materialisation error, never an invalid Quantity. A union without fields is stored as its case names in snake_case. A union with fields is spread over columns, here status and status_reason. A typed id is a reference to the record whose key it is.

/// Only valid quantities exist.
type Quantity =
    private | Quantity of int
    member q.Value = let (Quantity v) = q in v
    static member create(v: int) : Result<Quantity, string> =
        if v > 0 then Ok(Quantity v) else Error $"quantity must be positive, got {v}"

/// A cancelled order always says why: the reason is part of the case.
type OrderStatus =
    | Draft
    | Published
    | Cancelled of reason: string

// Typed ids and union cases are sent as their stored values.
let lookup (id: OrderId) =
    plasm { for o in tableOf<Order> do where (o.Id = id && o.Status = Draft) }

let! found = repo.All(lookup (OrderId 2L))

A record with a field type that has no convention fails at start-up, with the model and the property named:

Invalid persistence configuration:
  - Shipment.Weight: type UInt64 has no persistence mapping ...

3 · Composable queries

A query is an immutable value, and building one never touches the database. Reusable filters are ordinary functions from query to query. Captured values always travel as parameters. Another aggregate can be a condition, through exists (plasm { ... }). The record's own lists are read as F# reads a list, and a domain member marked [<ReflectedDefinition>] can be used too.

let forCustomer customerId (q: Query<Order>) =
    plasm { for o in q do where (o.CustomerId = Some customerId) }

// Payments are another aggregate: a correlated NOT EXISTS, so an order never appears twice.
let unpaid (q: Query<Order>) =
    plasm {
        for o in q do
            where (not (exists (plasm { for p in tableOf<Payment> do where (p.OrderId = o.Id && p.Status = Succeeded) })))
    }

let overdue customerId = Query.from (tableOf<Order>) |> forCustomer customerId |> unpaid

// In the domain:  [<ReflectedDefinition>] member o.IsOpen = match o.Status with Cancelled _ -> false | _ -> true
let openWithProduct (product: ProductId) =
    plasm {
        for o in tableOf<Order> do
            where (o.IsOpen && (o.Lines |> List.exists (fun l -> l.ProductId = product)))
    }

let! late = repo.All(overdue ada.Id)
F# semantics carry over to SQL: o.CustomerId = None becomes IS NULL, List.contains o.Id [] becomes FALSE, which is still valid SQL, and List.forall over an owned list means what it means in F#, so it is true for an empty list.

4 · Owned records

What a record owns is part of it, so there is nothing to request: every query of orders brings their lines. The orders are chosen first, with ordering and paging exactly as written. Their lines then follow in one command per batch of order keys. A page needs two commands, whether it holds 20 orders or 1,000.

let orderPage page size (q: Query<Order>) =
    plasm {
        for o in q do
            orderByDescending o.PlacedAt   // the key is appended as a tiebreaker
            skip (page * size)
            take size
    }

let! orders = repo.All(Query.from (tableOf<Order>) |> forCustomer ada.Id |> orderPage 0 20)

for o in orders do
    printfn "%A: %d lines" o.Id o.Lines.Length   // always read; [] means no lines
There is no unloaded state, so an empty list always means the order has no lines. A whole record read from a join or from hand-written SQL comes with what it owns as well.

5 · Other aggregates, by id

An order refers to its customer, and a payment to its order, by id. To read another aggregate for the records you hold, query it by their ids. List.contains over a list argument becomes one array parameter, so a prepared query works for any number of orders.

let succeededPaymentsOf =
    Query.prepare (fun (orders: Arg<OrderId list>) ->
        plasm {
            for p in tableOf<Payment> do
                where (List.contains p.OrderId orders.Value && p.Status = Succeeded)
                orderBy p.CreatedAt
        })

let! payments = repo.All(succeededPaymentsOf (orders |> List.map (fun o -> o.Id)))
let byOrder = payments |> List.groupBy (fun p -> p.OrderId) |> Map.ofList

6 · Projections and plans

A projection reads only the columns it uses and builds no records. Calling Explain describes the plan without a database round trip.

let totals =
    plasm {
        for o in tableOf<Order> do
            orderBy o.Id
            select {| Id = o.Id; Total = o.Total; Version = o.Version |}
    }

let! rows = repo.All totals
// Ok [{| Id = OrderId 1L; Total = 19.98M; Version = 3 |}; ...]

match repo.Explain(Query.from (tableOf<Order>) |> orderPage 0 20) with
| Ok plan -> plan.LoadPaths, plan.Sql
| Error e -> failwithf "%O" e
// (["Lines"], "SELECT ... FROM "orders" AS "t0" ORDER BY "t0"."placed_at" DESC, "t0"."id" ASC LIMIT @p0 OFFSET @p1")

7 · Transactions

Every write is a step of a transaction, and a transaction is a value: Tx<'T, 'E> gives a 'T or fails, and its own refusals are of your type 'E. let! passes typed results between steps, and repo.Transact runs them atomically. A step needs no name: a failure names the file and line where its step is written. The domain decides, and Tx.ofResult turns its Error into a rejection.

type Refusal =
    | Domain of OrderError
    | Missing of what: string

let checkout (customer: Customer) (lines: OrderLine list) (now: DateTime) : Tx<Customer * Order, Refusal> =
    transaction {
        let! stored = Tx.insert customer                                   // with its generated key
        let! order = Order.create stored.Id lines now |> Tx.ofResult Domain
        let! placed = Tx.insert order                                      // and its lines
        return stored, placed
    }

match! repo.Transact(checkout ada lines DateTime.UtcNow) with
| Ok(customer, order) -> printfn "order %A for %s" order.Id customer.Name
| Error { Failure = TxFailure.Rejected r; RolledBack = steps } -> printfn "refused: %A; rolled back %A" r steps
| Error e -> printfn "failed at %O: %A" e.Step e.Failure

// A single write needs its error type: repo.Transact(Tx.insert product : Tx<Product, Refusal>)
refused: Domain NoLines; rolled back ["Writes.fs:23 (insert Customer)"]
A transaction with no steps succeeds without opening a connection. Retries are opt-in (retry = RetryPolicy.OnSerializationFailure 3) and re-run the whole transaction, reads included.

8 · Changing a record

Read the record, let the domain decide, and write the record it decided. Tx.update (original, changed) writes only the columns that differ from the record read, and what the record owns is written by difference: a line left out is deleted, a new one is inserted. expectVersion is the version the caller last saw, for a copy that came back from a client.

let changeOrder (id: OrderId) (seen: int) (decide: Order -> Result<Order, OrderError>) : Tx<Order, Refusal> =
    transaction {
        let! order = Tx.one (orderById id) |> Tx.orReject (Missing "order")
        let! changed = decide order |> Tx.ofResult Domain
        return! Tx.update (order, changed, expectVersion = seen)
    }

// The domain removes the gadget line and recomputes the total.
let! trimmed = repo.Transact(changeOrder order.Id order.Version (Order.removeLines (fun l -> l.ProductId = gadget.Id)))

// Cancelled carries its reason, so the case writes two columns.
let! cancelled = repo.Transact(changeOrder order.Id trimmed.Version (Order.cancel "changed my mind"))
A line that belongs to another order is refused, not moved. Deleting an order (Tx.delete order) deletes its lines with it.

9 · Handling failures

Your refusals, invalid changes, concurrency conflicts and database failures are separate cases of TxFailure, so none of them needs message parsing. A constraint with PostgreSQL's default name (<table>_<column>_key, _fkey or _check) is that field's error.

match! repo.Transact(checkout eve lines now) with
| Ok _ -> ...
| Error { Failure = TxFailure.Rejected refusal } -> ...         // the domain said no
| Error { Failure = TxFailure.InvalidChanges(entity, errors) } -> showErrors errors
| Error { Failure = TxFailure.Conflict entity } -> reloadAndRetry ()   // a newer version is stored
| Error { Failure = TxFailure.Failed e } -> report e             // undeclared constraint, timeout, ...
| Error { Failure = TxFailure.Misused m } -> ...                // a Tx.run step tried to end the transaction
("Customer", [{ Field = "Email"; Message = "has already been taken"
                Kind = UniqueConstraint "customers_email_key" }])
("Order", [{ Field = "Lines[0].ProductId"; Message = "does not exist"
             Kind = ForeignKeyConstraint "order_lines_product_id_fkey" }])

An expression that can't be translated is never quietly run in memory:

let isLucky (d: decimal) = d = 7m
let! r = repo.All(plasm { for o in tableOf<Order> do where (isLucky o.Total) })
Error (Translation (UnsupportedExpression ("isLucky o.Total",
  "predicate cannot be translated to SQL and will not be evaluated in application memory")))

10 · Joins

A join combines rows from several tables in one command. An inner join keeps only matching pairs. A left join keeps every row and types the joined record as an option, so F# makes you handle the missing case. Joins chain into flat tuples, and a projection reads only the columns it names.

// (Order * Customer) list: orders without a customer are left out.
let ordersWithCustomers =
    plasm {
        for o in tableOf<Order> do
            join c in tableOf<Customer> on (o.CustomerId = Some c.Id)
            orderBy o.Id
    }

// Every order once; c is a Customer option.
let customerEmails =
    plasm {
        for o in tableOf<Order> do
            leftJoin c in tableOf<Customer> on (o.CustomerId = Some c.Id)
            orderBy o.Id
            select (o.Id, c |> Option.map (fun c -> c.Email))
    }

// Chained joins: the variable space is (o, l, p).
let soldProducts =
    plasm {
        for o in tableOf<Order> do
            join l in tableOf<OrderLine> on (o.Id = l.OrderId)
            join p in tableOf<Product> on (l.ProductId = p.Id)
            where o.IsOpen
            orderBy p.Sku
            select (o.Id, p.Sku, l.Quantity)
    }

let! emails = repo.All customerEmails     // [(OrderId 1L, Some "ada@example.com"); ...; (OrderId 3L, None)]
// Left-joined sources keep F# option semantics in SQL:
where c.IsNone                                           // anti-join: no matching customer
where (c |> Option.exists (fun c -> c.Name = "Ada"))    // matched, and the predicate holds
orderBy (c |> Option.map (fun c -> c.Name))             // missing customers first, like None < Some
A join returns one row per matching pair, so an order with three lines appears three times in the chained join. To filter orders by another aggregate without duplicates, use exists (example 3).

12 · Counts and aggregates

Counting, totals and grouped summaries run in the database, so no rows are fetched only to be counted or added up in memory. Aggregates are ordinary functions inside the query, and their types carry the F# meaning: the sum of nothing is 0, as with List.sum [], while min, max and avg return an option.

let! n = repo.Count published               // Result<int64, DbError>; one row transferred
let! any = repo.Exists published            // reads at most one row

// One row of statistics: int64 * decimal * decimal option * DateTime option
let orderStats =
    plasm {
        for o in tableOf<Order> do
            where o.IsOpen
            select (Agg.count (), Agg.sum o.Total, Agg.avg o.Total, Agg.max o.PlacedAt)
    }

let! stats = repo.One orderStats

// Customers with more than one order, biggest spenders first
let revenueByCustomer =
    plasm {
        for o in tableOf<Order> do
            join c in tableOf<Customer> on (o.CustomerId = Some c.Id)
            groupBy c.Name
            having (Agg.count () > 1L)
            orderByDescending (Agg.sum o.Total)
            select (c.Name, Agg.count (), Agg.sum o.Total)
    }
Summing text or averaging an integer key doesn't compile: Agg.sum and Agg.avg have the same constraints as List.sum and List.average. Selecting a column that is neither grouped nor aggregated, or using Agg in where, is rejected when the query is planned, before any command is sent.

13 · Bulk writes and upserts

A set-based change is one statement. You write the update as a copy-and-update expression: fields you assign are written, fields you leave alone are not, and assigned values can read the current row (o.Total + 10m). Bulk writes are values like queries, Tx.execute runs them as a transaction step, and repo.Explain shows their SQL.

let expireDrafts (before: DateTime) =
    Bulk.update (
        plasm { for o in tableOf<Order> do where (o.Status = Draft && o.PlacedAt < before) },
        fun o -> { o with Status = Cancelled "expired" }
    )

let! expired = repo.Transact(Tx.execute (expireDrafts DateTime.UtcNow) : Tx<int, Refusal>)   // rows updated

// Insert new products; rename existing ones, matched on the unique SKU
let syncCatalogue (products: Product list) =
    Bulk.upsert (products, (fun p -> p.Sku), fun current incoming -> { current with Name = incoming.Name })

// Also: Bulk.delete query, Bulk.insert records, Bulk.insertMissing (records, fun p -> p.Sku)
A bulk write runs no per-record decision, so use one only where the domain would accept every row it touches. Database constraints still apply and each statement is atomic. A bulk update increments the version column, so a copy read before it is stale. A bulk update that orders or pages, or assigns the key or the version, is rejected before it runs.

14 · Hand-written SQL

When the query language can't say something, write the SQL yourself and keep the types. repo.Sql takes an interpolated string, and every {value} becomes a command parameter. Rows come back as mapped records (columns by name, with what they own), other records (fields by name or snake_case name), tuples (columns in order) or single values. Inside a transaction the same is Tx.sql, and a hand-written command is Tx.executeSql.

let minimum = 5m

let! counts =
    repo.Sql<string * int64>(
        $"SELECT c.name, count(o.id) FROM customers c JOIN orders o ON o.customer_id = c.id
          WHERE o.total >= {minimum} GROUP BY c.name ORDER BY c.name")

let! orders = repo.Sql<Order>($"SELECT * FROM orders WHERE id = ANY({ids})")   // lists become one array

// A fragment of SQL inside a typed query
let customersMatching (pattern: string) =
    plasm {
        for c in tableOf<Customer> do
            where (Raw.fragment<bool> "{0} ILIKE {1}" (c.Name, pattern))
            orderBy c.Name
    }
A plain string doesn't type-check where SQL is expected, so values can't be pasted into SQL text by accident. A fragment's SQL is typed as an F# format string, which the compiler accepts only as a literal; write %% for a literal %. A missing column is reported with the field that needed it.

15 · Prepared queries

A hot path can build its query once. Query.prepare, prepare2 and prepare3 take a function of typed arguments and return a function to a query. The query is built and planned once, and each call only binds the arguments, so every call sends the same SQL text. Reading one order and its payments took 0.48 ms with two prepared queries, against 0.80 ms when both queries were rebuilt for each call.

let latestOrdersOf =
    Query.prepare2 (fun (customer: Arg<CustomerId>) (size: Arg<int>) ->
        plasm {
            for o in tableOf<Order> do
                where (o.CustomerId = Some customer.Value)
                orderByDescending o.PlacedAt
                take size.Value
        })

let! adas = repo.All(latestOrdersOf ada.Id 5)          // CustomerId -> int -> Query<Order>
let! bobs = repo.All(latestOrdersOf bob.Id 20)
let! n = repo.Count(latestOrdersOf ada.Id 5)           // works anywhere a query does
Optional arguments compare with IS NOT DISTINCT FROM, and list arguments use = ANY(@p), so the SQL is the same for None and for empty lists. Reading .Value while the query is being built, or ordering by an argument, fails when you prepare the query.

16 · Linked records

A list of stored records that don't hold the owner's key is linked, through the join table its field names with [<JoinTable>]: an article's tags. The join table's columns are named after the two records (article_id and tag_id) unless [<JoinTable>] names them, and [<OrderedBy>] says the tags are read in name order. The links are always read with the article, in one more command per batch of articles, and a tag linked to several articles is materialised once and shared between them. Writing the article writes only its links. The tags themselves are their own records, so the transaction makes sure they exist first.

/// A tag, shared by the articles that link to it.
[<Table "tags">]
type Tag =
    { Id: TagId
      [<Unique>]
      Name: string }

/// An article links to shared tags, which hold no article's key: writing the
/// article writes only the links.
[<Table "articles">]
type Article =
    { Id: ArticleId
      Title: string
      [<JoinTable "article_tags"; OrderedBy(nameof the<Tag>.Name)>]
      Tags: Tag list }

// Makes `names` the article's complete set of tags.
let retag (article: Article) (names: string list) : Tx<Article, Refusal> =
    transaction {
        let! _ = Tx.execute (Bulk.insertMissing ([ for n in names -> { Id = TagId 0L; Name = n } ], fun t -> t.Name))
        let! tags = Tx.all (tagsNamed names)
        return! Tx.update (article, { article with Tags = tags })
    }

let! all = repo.All(plasm { for a in tableOf<Article> do orderBy a.Id })   // with their tags
let! retagged = repo.Transact(retag intro [ "fsharp"; "sql" ])
let! tagged = repo.All(plasm { for a in tableOf<Article> do where (a.Tags |> List.exists (fun t -> t.Name = "fsharp")) })
A link to a tag that doesn't exist is the field's error (the join table's _fkey). Changing a tag through the article is refused: a tag is changed by its own transaction. Deleting an article deletes its links, never its tags.

17 · Checks and the sandbox

Plasm doesn't migrate schemas, so keep your migration tool. repo.Ddl() prints the tables the model expects, with constraints under the names Plasm maps violations by, for you to write the migration from. At start-up, repo.CheckSchema compares the model with the live database, and repo.CheckQueries translates every query an assembly defines as a value, without running any. In tests, repo.Sandbox runs code against the real database inside a transaction that is always rolled back.

printfn "%s" (repo.Ddl())
// create table orders (
//   id bigint not null generated always as identity primary key,
//   customer_id bigint, status text not null, status_reason text, ...
// alter table orders add constraint orders_customer_id_fkey foreign key (customer_id) references customers (id);

// At start-up
match repo.CheckQueries(typeof<Order>.Assembly, "Shop") with
| [] -> ()
| problems -> failwithf "queries that cannot be translated: %A" problems

match! repo.CheckSchema() with
| Ok [] -> ()
| Ok issues -> failwithf "the database does not match the model:\n%s" (issues |> List.map string |> String.concat "\n")
| Error e -> failwithf "could not read the catalogue: %A" e

// In a test: nothing written inside survives
let! count =
    repo.Sandbox(fun repo ->
        task {
            let! _ = repo.Transact(Tx.insert test : Tx<Customer, Refusal>)
            let! n = repo.Count(Query.from (tableOf<Customer>))
            return n
        })
The schema check reports missing tables and columns (join tables included), incompatible types, non-optional fields over nullable columns, NOT NULL columns the model never writes, and unique fields and references without their constraint. Inside a sandbox, transactions become savepoints and each operation runs in its own savepoint, so a constraint violation doesn't break the rest of the test.

18 · F# Interactive

Plasm is built to be explored in F# Interactive. Referencing the package is the only setup. A query displays the SQL it would run, with its parameter values and the command that reads what its records own; displaying it never touches the database. The code is examples/fsi-tour.fsx (with its references and connection string shortened), and the output below each part is what dotnet fsi printed for it against PostgreSQL.

#r "nuget: Plasm.Postgres"             // until published: #r the two built DLLs
#load "Plasm.Examples/Model.fs"
open Plasm
open Plasm.Postgres
open Plasm.Interactive                  // wait: show a result, not a task
open Shop.Model

A playground is a repository whose changes last across submissions but are never committed, so you can try transactions against real data. Reset rolls everything back and keeps it open; Close ends it.

let pg = repo.Playground();;
pg.Transact(Tx.insert { Id = CustomerId 0L; Name = "Ada"; Email = "ada@example.com" }: Tx<Customer, unit>) |> wait;;
pg.All(plasm { for c in tableOf<Customer> do orderBy c.Name }) |> wait;;
pg.Reset();;
pg.All(plasm { for c in tableOf<Customer> do orderBy c.Name }) |> wait;;
val it: Result<Customer,TransactionError<unit>> =

       Name = "Ada"
       Email = "ada@example.com" }

repo.Scaffold reads a table from the catalogue and prints a record for it, with its [<Table>]. Column types map back through the dialect, so the result passes the schema check; nullable columns become options, and columns with no F# type are left out with a comment. A column is named after its field, in snake_case, unless [<Column>] says otherwise, so a column whose name the field's can't produce is printed with [<Column "...">]. The primary key becomes the field named Id, marked [<Assigned>] when it is an integer the database doesn't generate.

repo.Scaffold "payments" |> wait;;
val it: Result<Scaffold,ScaffoldError> =
  Ok

[<Table "payments">]
type Payment =
    { Id: int64
      OrderId: int64
      Amount: decimal
      Status: string
      CreatedAt: System.DateTime }

Scaffolding doesn't infer what a record owns, and scaffolded keys are plain int64. Wrap them in single-case unions like OrderId when you adopt the record; the convention stores them, and a typed id becomes a reference.
