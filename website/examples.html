Examples

These examples follow one shop domain from start to finish. The snippets come from the runnable tour in examples/Plasm.Examples, and the outputs shown are what it printed against PostgreSQL.

Each example can switch to the SQL Plasm generated for it, with the parts that make that example different highlighted. The SQL is captured from the library's diagnostics while the examples run, not written by hand.

Run the tour

The tour provisions a throwaway PostgreSQL database with Testcontainers. To use a server you already have, set PLASM_TEST_PG to an admin connection string.

dotnet run --project examples/Plasm.Examples

1 · Model and schemas

The domain is plain immutable records. Persistence metadata lives in separate schema values rather than in attributes or base classes. A relationship field records whether it was loaded, and the shape of its payload gives the cardinality: Assoc<X list> is has-many, Assoc<X option> is optional, and Assoc<X> is required.

type OrderId = OrderId of int64
type OrderStatus = Draft | Published | Cancelled

type Order =
    { Id: OrderId
      CustomerId: CustomerId option
      Status: OrderStatus
      Total: decimal
      CancellationReason: string option
      PlacedAt: DateTime
      Version: int
      Customer: Assoc<Customer option>   // optional belongs-to
      Lines: Assoc<OrderLine list>      // has-many
      Payments: Assoc<Payment list> }   // has-many

and OrderLine =
    { Id: OrderLineId; OrderId: OrderId; ProductId: ProductId
      Quantity: Quantity; UnitPrice: decimal
      Product: Assoc<Product> }         // required belongs-to

module Db =
    let orders =
        schema<Order> "orders" {
            identityKey (fun o -> o.Id)                // generated by the database
            version (fun o -> o.Version)               // optimistic concurrency
            belongsTo (fun o -> o.Customer) (fun o -> o.CustomerId)
            hasMany (fun o -> o.Lines) (fun l -> l.OrderId) OnReplace.Delete
            hasMany (fun o -> o.Payments) (fun p -> p.OrderId)
        }

    let orderLines =
        schema<OrderLine> "order_lines" {
            identityKey (fun l -> l.Id)
            belongsTo (fun l -> l.Product) (fun l -> l.ProductId)
        }

let! all = repo.All(Query.from Db.orders)

Every selector is a typed lambda, so there are no string property paths. Column names default to snake_case.

2 · Scalars and model validation

Wrapper types and unions are stored only through mappings you declare, and nothing is converted implicitly. A validating constructor is never bypassed, so a stored zero quantity becomes a structured materialisation error rather than an invalid Quantity.

let scalars =
    [ Scalar.wrap OrderId (fun (OrderId v) -> v)
      Scalar.tryWrap Quantity.create (fun (q: Quantity) -> q.Value)
      Scalar.enum [ Draft, "draft"; Published, "published"; Cancelled, "cancelled" ] ]

// Checked once at start-up; every problem is reported at once.
let model = Model.buildOrFail scalars [ customers; orders; orderLines; products; payments ]

// Wrapped ids and union cases are sent as their stored values.
let lookup (id: OrderId) =
    plasm { for o in Db.orders do where (o.Id = id && o.Status = Draft) }

let! found = repo.All(lookup (OrderId 1L))

A record with a field type that has no mapping fails with the model and the property named:

Invalid persistence configuration:
  - Shipment.Destination: type Address has no persistence mapping; register Scalar.wrap, Scalar.tryWrap or Scalar.enum
  - Shipment.Weight: type UInt64 has no persistence mapping; register Scalar.wrap, Scalar.tryWrap or Scalar.enum

3 · Composable queries

A query is an immutable value, and building one never touches the database. Reusable filters are ordinary functions from query to query. Captured values always travel as parameters.

let published = plasm { for o in Db.orders do where (o.Status = Published) }

let forCustomer customerId (q: Query<Order>) =
    plasm { for o in q do where (o.CustomerId = Some customerId) }

// A relationship predicate becomes EXISTS, so an order never appears twice.
let unpaid (q: Query<Order>) =
    plasm { for o in q do where (not (o.Payments |> Rel.any (fun p -> p.Status = Succeeded))) }

let overdue customerId = Query.from Db.orders |> forCustomer customerId |> unpaid

let! late = repo.All(overdue ada.Id)
F# semantics carry over to SQL: o.CancellationReason = None becomes IS NULL, and List.contains o.Id [] becomes FALSE, which is still valid SQL.

4 · Relationship loads

Child queries are reusable values too. They can filter, order and nest further loads. A per-parent limit is stated explicitly, and a plain take inside a load query is rejected.

let linesWithProducts = plasm { for l in Db.orderLines do preload l.Product }

let successfulPayments =
    plasm {
        for p in Db.payments do
            where (p.Status = Succeeded)
            orderBy p.CreatedAt
    }

let latestPayments n =
    plasm {
        for p in Db.payments do
            orderByDescending p.CreatedAt
            limitPerParent n               // per order, never global
    }

let orderPage page size (q: Query<Order>) =
    plasm {
        for o in q do
            orderByDescending o.PlacedAt   // the primary key is appended as a tiebreaker
            skip (page * size)
            take size
            preload o.Lines linesWithProducts
            preload o.Payments successfulPayments
    }

let! orders = repo.All(Query.from Db.orders |> forCustomer ada.Id |> orderPage 0 20)

// At most three payments per order: a window function, never a global LIMIT.
let recentPayments n = plasm { for o in Db.orders do preload o.Payments (latestPayments n) }
let! recent = repo.All(recentPayments 3)

The page loads in four commands, however many orders it holds:

SELECT … FROM "orders" AS "t0" WHERE ("t0"."customer_id" = @p0) ORDER BY "t0"."placed_at" DESC, "t0"."id" ASC LIMIT @p1 OFFSET @p2
SELECT … FROM "order_lines" AS "t0" WHERE ("t0"."order_id" = ANY(@p0)) ORDER BY "t0"."id" ASC
SELECT … FROM "products" AS "t0" WHERE ("t0"."id" = ANY(@p0)) ORDER BY "t0"."id" ASC
SELECT … FROM "payments" AS "t0" WHERE (("t0"."order_id" = ANY(@p0)) AND ("t0"."status" = @p1)) ORDER BY "t0"."created_at" ASC, "t0"."id" ASC
for o in orders do
    match o.Payments with
    | Loaded [] -> printfn "%A: loaded, no successful payments" o.Id
    | Loaded ps -> printfn "%A: %d payments" o.Id ps.Length
    | NotLoaded -> ()                // never happens here: it was requested
If two reusable functions customise the same relationship differently, the conflict is reported as LoadConflict before any command runs. Choose one explicitly with replacePreload.

6 · Projections and plans

A projection reads only the columns it uses and builds no entities. Calling Explain describes the plan without a database round trip.

let totals =
    plasm {
        for o in Db.orders do
            orderBy o.Id
            select {| Id = o.Id; Total = o.Total; Version = o.Version |}
    }

let! rows = repo.All totals
// Ok [{| Id = OrderId 1L; Total = 19.98M; Version = 2 |}]

match repo.Explain(Query.from Db.orders |> orderPage 0 20) with
| Ok plan -> plan.LoadPaths, plan.Loads |> List.map (fun l -> l.Path, l.Strategy)
| Error e -> failwithf "%O" e
// (["Lines"; "Lines.Product"; "Payments"],
//  [("Lines", BatchedByKeys 5000); ("Payments", BatchedByKeys 5000)])

7 · Changesets

A change is a value. Changeset.edit records exactly the fields your function alters, and setting an option to None records an explicit clear. External input is accepted one field at a time, so an id or version in a form is simply ignored.

let registerCustomer name email =
    Changeset.insert { Id = CustomerId 0L; Name = name; Email = email; Orders = NotLoaded }
    |> Changeset.validateFormat((fun c -> c.Email), "^[^@\\s]+@[^@\\s]+$")
    |> Changeset.uniqueConstraint((fun c -> c.Email), "customers_email_key")

let cancelFromForm (form: IReadOnlyDictionary<string, string>) (order: Order) =
    Changeset.update order
    |> Changeset.set((fun o -> o.Status), Cancelled)
    |> Changeset.cast(form, fun o -> o.CancellationReason)
    |> Changeset.validateRequired(fun o -> o.CancellationReason)

// Inspectable before anything runs:
(registerCustomer "Bob" "not-an-email").Errors
[{ Field = "Email"; Message = "has invalid format"; Kind = Format }]

When the full record isn't at hand, for example after a projection, write only the fields you name:

let publishByKey (id: OrderId) (version: int) =
    Changeset.forKey((fun (o: Order) -> o.Id), id)
    |> Changeset.expectVersion version
    |> Changeset.set((fun o -> o.Status), Published)

let! _ = repo.Insert(registerCustomer "Bob" "bob@example.com")
let! _ = repo.Update(order |> cancelFromForm form)   // form also holds "id" and "version"
let! _ = repo.Update(publishByKey summary.Id summary.Version)

8 · Child writes

A parent and its children are written in one transaction. New children get the parent's key, existing ones are updated by identity, and anything you don't mention is left alone. Replacing a set of children requires a scope, and removing omitted children requires a policy declared in the schema.

let placeOrder customer (lines: OrderLine list) =
    let total = lines |> List.sumBy (fun l -> decimal l.Quantity.Value * l.UnitPrice)

    Changeset.insert { newOrder customer with Total = total }
    |> Changeset.validateRange((fun o -> o.Total), min = 0m)
    |> Changeset.putChildren((fun o -> o.Lines), lines |> List.map Changeset.insert)

// Keep only these lines; Lines declares OnReplace.Delete, so the others are deleted.
let keepOnly (order: Order) (kept: OrderLine list) =
    Changeset.update order
    |> Changeset.replaceChildren((fun o -> o.Lines), ReplaceScope.allChildren, kept |> List.map Changeset.update)

let! placed = repo.Insert(placeOrder ada.Id [ widgetLine; gadgetLine ])
// Keep the first inserted line (it now has its generated id); delete the other.
let! trimmed = repo.Update(keepOnly placed (Assoc.get placed.Lines |> List.take 1))
With a filtered collection, name the filter: ReplaceScope.matching successfulPayments considers only successful payments, and the others are never touched.

9 · Transactions

A transaction is a description: let! passes typed results between named steps, and repo.Transact runs it atomically. A description with no steps succeeds without opening a connection. Retries are opt-in and re-run the whole description, reads included.

let checkout name email (product: ProductId) =
    transaction {
        let! customer = Tx.insert "customer" (registerCustomer name email)
        let! order = Tx.insert "order" (placeOrder customer.Id [ line product ])
        return customer, order
    }

match! repo.Transact(checkout "Ada" "ada@example.com" widget.Id,
                     retry = RetryPolicy.OnSerializationFailure 3) with
| Ok(customer, order) -> printfn "order %A for %s" order.Id customer.Name
| Error e -> printfn "failed at %s; rolled back %A" e.Step e.RolledBack
failed at second order; rolled back ["customer"; "first order"]

10 · Handling failures

Validation errors, concurrency conflicts and infrastructure failures are separate cases, so none of them needs message parsing.

match! repo.Update(order |> cancelFromForm form) with
| Ok cancelled -> ...
| Error(WriteError.Invalid cs) -> showErrors cs.Errors          // validation or declared constraint
| Error(WriteError.Stale _) -> reloadAndRetry ()               // a newer version is stored
| Error(WriteError.Failed { Kind = DbFailureKind.ConnectionFailure }) -> retryLater ()
| Error(WriteError.Failed f) -> report f                       // undeclared constraint, timeout, ...

An expression that can't be translated is never quietly run in memory:

// `order` was read at version 1; the form update above moved the row to version 2.
let! stale = repo.Update(order |> Changeset.edit (fun o -> { o with Total = 1m }))
// Error (WriteError.Stale _)

let isLucky (d: decimal) = d = 7m
let! r = repo.All(plasm { for o in Db.orders do where (isLucky o.Total) })
Error (Translation (UnsupportedExpression ("isLucky o.Total",
  "predicate cannot be translated to SQL and will not be evaluated in application memory")))

11 · Joins

A join combines rows from several tables in one command. An inner join keeps only matching pairs. A left join keeps every row and types the joined record as an option, so F# makes you handle the missing case. Joins chain into flat tuples, and a projection reads only the columns it names.

// (Order * Customer) list: orders without a customer are left out.
let ordersWithCustomers =
    plasm {
        for o in Db.orders do
            join c in Db.customers on (o.CustomerId = Some c.Id)
            orderBy o.Id
    }

// Every order once; c is a Customer option.
let customerEmails =
    plasm {
        for o in Db.orders do
            leftJoin c in Db.customers on (o.CustomerId = Some c.Id)
            orderBy o.Id
            select (o.Id, c |> Option.map (fun c -> c.Email))
    }

// Chained joins: the variable space is (o, l, p).
let soldProducts =
    plasm {
        for o in Db.orders do
            join l in Db.orderLines on (o.Id = l.OrderId)
            join p in Db.products on (l.ProductId = p.Id)
            where (o.Status <> Cancelled)
            orderBy p.Sku
            select (o.Id, p.Sku, l.Quantity)
    }

let! pairs = repo.All ordersWithCustomers
let! emails = repo.All customerEmails     // [(OrderId 1L, Some "ada@example.com"); ...; (OrderId 3L, None)]
let! sold = repo.All soldProducts
// Left-joined sources keep F# option semantics in SQL:
where c.IsNone                                           // anti-join: no matching customer
where (c |> Option.exists (fun c -> c.Name = "Ada"))    // matched, and the predicate holds
orderBy (c |> Option.map (fun c -> c.Name))             // missing customers first, like None < Some
A join returns one row per matching pair, so an order with three payments appears three times. To filter orders by their payments without duplicates, use a relationship predicate (Rel.any, example 3). To load whole graphs, use preload (example 4): preload on a joined query is rejected and points you to repo.Preload.

Both produce the same parent query: WHERE status = 'published' ORDER BY placed_at DESC, id LIMIT 20. They differ in how each child query is limited to those 20 orders. Switch to Generated SQL to compare: Plasm sends the 20 order ids as one array parameter, while EF Core runs the parent query again inside every child query. With 10,000 orders, a page of 1,000 took 16.5 ms in Plasm and 34.8 ms with EF's split query (BenchmarkDotNet means; see docs/benchmarks.md).

13 · Counts and aggregates

Counting, totals and grouped summaries run in the database, so no rows are fetched only to be counted or added up in memory. Aggregates are ordinary functions inside the query, and their types carry the F# meaning: the sum of nothing is 0, as with List.sum [], while min, max and avg return an option.

let! n = repo.Count published               // Result<int64, DbError>; one row transferred
let! any = repo.Exists published            // reads at most one row

// One row of statistics: int64 * decimal * decimal option * DateTime option
let orderStats =
    plasm {
        for o in Db.orders do
            where (o.Status <> Cancelled)
            select (Agg.count (), Agg.sum o.Total, Agg.avg o.Total, Agg.max o.PlacedAt)
    }

let! stats = repo.One orderStats

// Customers with more than one order, biggest spenders first
let revenueByCustomer =
    plasm {
        for o in Db.orders do
            join c in Db.customers on (o.CustomerId = Some c.Id)
            groupBy c.Name
            having (Agg.count () > 1L)
            orderByDescending (Agg.sum o.Total)
            select (c.Name, Agg.count (), Agg.sum o.Total)
    }
Summing text or averaging an integer key doesn't compile: Agg.sum and Agg.avg have the same constraints as List.sum and List.average. Selecting a column that is neither grouped nor aggregated, or using Agg in where, is rejected when the query is planned, before any command is sent.

14 · Bulk writes and upserts

A set-based change is one statement. You write the update as a copy-and-update expression: fields you assign are written, fields you leave alone are not, and assigned values can read the current row (o.Total + 10m). Bulk writes are values like queries: repo.Explain shows their SQL, and Tx.execute runs them as a transaction step.

let expireDrafts (before: DateTime) =
    Bulk.update (
        plasm { for o in Db.orders do where (o.Status = Draft && o.PlacedAt < before) },
        fun o -> { o with Status = Cancelled; CancellationReason = Some "expired" }
    )

let! expired = repo.Execute(expireDrafts DateTime.UtcNow)     // Result<int, DbError>: rows updated

// Insert new products; rename existing ones, matched on the unique SKU
let syncCatalogue (products: Product list) =
    Bulk.upsert (products, (fun p -> p.Sku), fun current incoming -> { current with Name = incoming.Name })

let! synced = repo.Execute(syncCatalogue catalogue)           // every inserted or updated Product

// Also: Bulk.delete query, Bulk.insert records, Bulk.insertMissing (records, fun p -> p.Sku)
Bulk writes skip changeset validation, as Ecto's update_all does, but database constraints still apply and each statement is atomic. Unlike Ecto, a bulk update increments the version column, so a changeset built from an older copy of the row is rejected as stale. A bulk update that orders or pages, or assigns the key or the version, is rejected before it runs.

15 · Hand-written SQL

When the query language can't say something, write the SQL yourself and keep the types. repo.Sql takes an interpolated string, and every {value} becomes a command parameter. Rows come back as mapped records (columns by name), other records (fields by name or snake_case name), tuples (columns in order) or single values.

let minimum = 5m

let! counts =
    repo.Sql<string * int>(
        $"SELECT c.name, count(o.id) FROM customers c JOIN orders o ON o.customer_id = c.id
          WHERE o.total >= {minimum} GROUP BY c.name ORDER BY c.name")

let! orders = repo.Sql<Order>($"SELECT * FROM orders WHERE id = ANY({ids})")   // lists become one array
let! changed = repo.ExecuteSql($"UPDATE orders SET total = total + 1 WHERE customer_id = {ada}")

// A fragment of SQL inside a typed query
let customersMatching (pattern: string) =
    plasm {
        for c in Db.customers do
            where (Raw.fragment<bool> "{0} ILIKE {1}" (c.Name, pattern))
            orderBy c.Name
    }
A plain string doesn't type-check where SQL is expected, so values can't be pasted into SQL text by accident. A fragment's SQL is typed as an F# format string, which the compiler accepts only as a literal; write %% for a literal %. A missing column is reported with the field that needed it.

16 · Prepared queries

A hot path can build its query once. Query.prepare takes a function of typed arguments and returns a function to a query. The query is built and planned once, and each call only binds the arguments, so every call sends the same SQL text. On a one-order lookup this cut the per-call time from 474 µs to 392 µs and allocations from 207 KB to 108 KB.

let latestOrdersOf =
    Query.prepare2 (fun (customer: Arg<CustomerId>) (size: Arg<int>) ->
        plasm {
            for o in Db.orders do
                where (o.CustomerId = Some customer.Value)
                orderByDescending o.PlacedAt
                take size.Value
        })

let! adas = repo.All(latestOrdersOf ada.Id 5)          // CustomerId -> int -> Query<Order>
let! bobs = repo.All(latestOrdersOf bob.Id 20)
let! n = repo.Count(latestOrdersOf ada.Id 5)           // works anywhere a query does
Optional arguments compare with IS NOT DISTINCT FROM, and list arguments use = ANY(@p), so the SQL is the same for None and for empty lists. Reading .Value while the query is being built, or ordering by an argument, fails when you prepare the query.

17 · Many-to-many

Declare the join table once. Loading is batched like any other relationship. A tag linked to several articles is materialised once and shared between them. Changing links writes only join-table rows; the tags themselves are never written.

type Article = { Id: ArticleId; Title: string; Tags: Assoc<Tag list> }
and Tag = { Id: TagId; Name: string }

let articles =
    schema<Article> "articles" {
        identityKey (fun a -> a.Id)
        manyToMany (fun a -> a.Tags) "article_tags" "article_id" "tag_id"
    }

let articlesWithTags =
    plasm {
        for a in Db.articles do
            orderBy a.Id
            preload a.Tags (plasm { for t in Db.tags do orderBy t.Name })
    }

// The complete set of tags; the returned article has them loaded
let retag article tags = Changeset.update article |> Changeset.putLinks ((fun a -> a.Tags), tags)

let! retagged = repo.Update(retag intro [ fsharp; sql ])
let! tagged = repo.All(plasm { for a in Db.articles do where (Rel.any (fun t -> t.Name = "fsharp") a.Tags) })
addLinks and removeLinks change only the links you name. Afterwards the relationship is NotLoaded, because the full set wasn't read. Links only point at stored records: linking to one that doesn't exist fails with a foreign-key violation and rolls back the whole write. A join table with its own columns is better modelled as a record with two belongsTo relationships.

18 · Schema check and test sandbox

Plasm doesn't migrate schemas, so keep your migration tool. At start-up, repo.CheckSchema compares the model with the live database and reports every difference that would make a read or write fail. In tests, repo.Sandbox runs code against the real database inside a transaction that is always rolled back.

// At start-up
match! repo.CheckSchema() with
| Ok [] -> ()
| Ok issues -> failwithf "the database does not match the model:\n%s" (issues |> List.map string |> String.concat "\n")
| Error e -> failwithf "could not read the catalogue: %A" e
// e.g. "NullableColumn Order.CancellationReason (orders.cancellation_reason): column is nullable
//       but Order.CancellationReason is not optional; a NULL would fail to load. ..."

// In a test: nothing written inside survives
let! count =
    repo.Sandbox(fun repo ->
        task {
            let! _ = repo.Insert(registerCustomer "Test" "test@example.com")
            let! n = repo.Count(Query.from Db.customers)
            return n
        })
The check reports missing tables and columns (join tables included), incompatible types, non-optional fields over nullable columns, and NOT NULL columns the model never writes. Inside a sandbox, transactions become savepoints and each operation runs in its own savepoint, so a constraint violation doesn't break the rest of the test. Concurrent sandboxes are isolated from each other like ordinary transactions.
