Ecto's design · expressed in F#

Persistence that thinks in F#.

Immutable records, compiler-checked queries, explicit changesets and batched relationship loading. Queries, changes and transactions are values; the repo is the only place anything touches the database.

Six things it won't do behind your back

Each one is an executable Gherkin scenario, run against a real PostgreSQL database.

No hidden database access

Relationships are NotLoaded | Loaded of 'T. Reading one never queries, and empty and unloaded are different values.

Nothing runs client-side by accident

A predicate that can't become SQL fails with the expression named. Rows are never fetched to be filtered in memory.

No N+1, no cartesian product

Each relationship is one command per batch of parent keys. Sibling collections load separately.

Limits mean what they say

limitPerParent 3 is per parent. A plain take in a load query is rejected as ambiguous.

Typed throughout

Comparing o.Total with a string, loading a field that isn't a relationship, or mixing OrderId with CustomerId won't compile.

Partial data can't destroy data

Unmentioned fields are never written. Replacing children needs an explicit scope and a declared removal policy.

How a page of orders loads

The parent page is chosen first. Each relationship then receives exactly the selected keys as one array parameter. Records are built once, bottom-up, and shared products are a single immutable value.

  1. 1 · parentordersORDER BY placed_at DESC, id LIMIT 20
  2. 2 · has manyorder_linesorder_id = ANY(@keys)
  3. 3 · belongs to, nestedproductsid = ANY(@distinct keys)
  4. 4 · has many, filteredpaymentsorder_id = ANY(@keys) AND status = @p1

You can inspect any plan without touching the database: repo.Explain query returns the SQL, the load paths and the batching strategy.

Changes are values

Unchanged, assigned and cleared are three different states. Validation is pure and can be inspected before anything runs.

let cs =
    order
    |> Changeset.edit (fun o -> { o with Status = Cancelled })
    |> Changeset.validateRange((fun o -> o.Total), min = 0m)

match! repo.Update cs with
| Ok updated -> ...
| Error(WriteError.Invalid cs) -> cs.Errors   // per field
| Error(WriteError.Stale _)    -> ...         // newer version stored
| Error(WriteError.Failed f)   -> f.Kind      // classified failure

So are transactions

Named steps pass typed results with let!. A failure names the step and what was rolled back. Retries are opt-in.

let checkout name email product =
    transaction {
        let! customer = Tx.insert "customer" (registerCustomer name email)
        let! order = Tx.insert "order" (placeOrder customer.Id [ line ])
        return customer, order
    }

match! repo.Transact(checkout "Ada" "ada@example.com" widget) with
| Ok (customer, order) -> ...
| Error e -> printfn "%s failed; rolled back %A" e.Step e.RolledBack

Honest status

An experimental first delivery, not production-ready. Ecto's design transfers; its operational maturity has to be earned.

135 / 135 acceptance scenarios · 176 unit, property and compile-time tests

Works today

  • Typed queries, projections, relationship predicates
  • Inner and left joins, with option-typed left sides
  • Nested batched loads, per-parent limits, snapshots
  • Changesets, constraints, optimistic concurrency
  • Atomic child writes, transactions, retries
  • Count, exists, aggregates, group by and having
  • Bulk update, delete, insert and upsert
  • Typed hand-written SQL; prepared queries
  • Many-to-many; schema check; test sandboxes

Not yet

  • Right and full joins, unions, CTEs
  • Composite keys, JSON columns
  • Prepared projections; packaging
  • Databases other than PostgreSQL
