A stricter data layer for your C# application.

Your domain types, rules and queries go in one small F# project. Your ASP.NET application calls it like any other library.

ASP.NET, your host and your team's C# stay as they are. In the F# project Plasm stores immutable records, checks every query and makes every write a typed transaction. C# calls plain async methods and switches over the outcomes. All of it compiles ahead of time.

/// A page of orders, each with its lines: two commands however long the page.
let orderPage page size (q: Query<Order>) =
    plasm {
        for o in q do
            orderByDescending o.PlacedAt // the key is appended as a tiebreaker
            skip (page * size)
            take size
    }

Why not EF Core?

The same endpoint, both ways

Book a piece of equipment for someone. It can be missing, out of service, already taken, changed by someone else since you read it, or the request can be invalid. Both versions handle all of that. The difference is who remembers to.

Where they differ

The data layer is one line, where AddDbContext would go

The build writes AddBookingData for you from the F# project. It takes its clock from the container and logs its SQL through ILogger.

When the host starts, Plasm checks every record and every query against the real schema. If they disagree, the application stops before it serves a request.

A request arrives at an endpoint

ASP.NET binds the route and the body and injects BookingData. The endpoint passes the request on whole and turns the answer into an HTTP result with .ToHttp().

That is the entire endpoint.

app.MapPost("/equipment/{id:guid}/bookings", (Guid id, NewBooking input, BookingData d, CancellationToken ct) =>
    d.BookAsync(id, input, ct).ToHttp());

The model: a record is a table

This is the whole model for equipment and its bookings. Records are immutable. The attributes say how each is stored, so there is no separate mapping class and no migration to keep in step.

A piece of equipment owns its bookings: they are read, changed and deleted with it, in order of their start.

[<Table "bookings">]
type Booking =
    { Id: BookingId
      Equipment: EquipmentId
      Who: string
      From: DateTimeOffset
      Until: DateTimeOffset }

[<Table "equipment">]
type Equipment =
    { Id: EquipmentId
      [<Unique>]
      Name: EquipmentName
      Condition: Condition
      [<OrderedBy(nameof the<Booking>.From)>]
      Bookings: Booking list
      [<Version>]
      Version: int }

A union says exactly which states exist

In C# this would be an enum, a nullable reason and a nullable date, with nothing stopping an available item from carrying a reason. Here the reason and the date exist only when the equipment is out of service.

Add a third case later and the compiler lists every place that must now handle it.

type Condition =
    | Available
    | OutOfService of reason: string * since: DateTimeOffset

Values that cannot be wrong, ids that cannot be mixed up

An EquipmentName can only be made by create, so every name in the program is 1 to 60 characters, trimmed. Plasm reads stored names through the same function.

An EquipmentId and a BookingId are both a Guid underneath, but passing one where the other belongs does not compile.

type EquipmentId = EquipmentId of Guid
type BookingId = BookingId of Guid
// ...
type EquipmentName =
    private
    | EquipmentName of string
// ...
    static member create(text: string | null) : Result<EquipmentName, string> =
        let t = (match text with null -> "" | t -> t).Trim()

        if t.Length = 0 then Error "is required"
        elif t.Length > 60 then Error "must be at most 60 characters"
        else Ok(EquipmentName t)

Queries are typed values, checked before the first request

A query is written against the record, not against strings. Reading an Equipment brings its bookings with it.

Plasm finds every query in the project when the application starts and checks it against the real schema, so a query that would fail fails then, not when a customer reaches it.

let byId =
    Query.prepare (fun (id: Arg<EquipmentId>) -> plasm { for e in tableOf<Equipment> do where (e.Id = id.Value) })

/// Every piece of equipment, ordered by name.
let byName = plasm { for e in tableOf<Equipment> do orderBy e.Name }

A rule is a plain function

It is handed the equipment as it is now and answers with the changed record or a named refusal. There is no database in it, so it is tested without one.

Leave out a case of Condition and the F# compiler says which one is missing.

let book (id: BookingId) (who: string) (from: DateTimeOffset) (until: DateTimeOffset) (equipment: Equipment) =
    if String.IsNullOrWhiteSpace who then
        Error WhoRequired
    elif until <= from then
        Error EndsBeforeItStarts
    else
        match equipment.Condition with
        | OutOfService(reason, _) -> Error(NotAvailable reason)
        | Available ->
            match equipment.Bookings |> List.tryFind (overlaps from until) with
            | Some taken -> Error(AlreadyBooked taken.Who)
            | None ->
                // ...
                Ok { equipment with Bookings = equipment.Bookings @ [ booking ] }

A change names the record, the version seen and the rule

This is the method the endpoint called. Plasm does the rest in one transaction: read the record, apply the rule, write the result.

If someone else changed the record since the caller read it, the version does not match and nothing is written.

member _.BookAsync(id: EquipmentId, request: NewBooking, cancellationToken: CancellationToken) =
    let booking = BookingId(Guid.CreateVersion7())
    let from = request.From.ToUniversalTime()
    let until = request.Until.ToUniversalTime()
    let rule = Equipment.book booking request.Who from until
    repo.Change(Db.byId id, request.Version, rule, cancellationToken)

The table is what the record said

Plasm prints this DDL from the records; you run it. The union became a column and two that are filled only when it is out of service. The version column is what refuses a stale write.

Plasm checks the schema at start and never alters an existing database. Store.fs is the one file that knows whether this is PostgreSQL or SQLite.

create table equipment (
  id uuid not null primary key,
  name text not null,
  condition text not null,
  condition_reason text,
  condition_since timestamp with time zone,
  version integer not null default 1,
  constraint equipment_name_key unique (name)
);

A refusal carries its own name and words

On the way back there is nothing to map by hand. A refusal reaches C# as Refused with the case name as its code and this message.

type Refusal =
    | WhoRequired
    | ReasonRequired
    | EndsBeforeItStarts
    | NotAvailable of reason: string
    | AlreadyBooked of by: string
// ...
    member refusal.Message =
        match refusal with
// ...
        | AlreadyBooked by -> $"{by} has it booked for some of that time."

Back across the seam as a C# union

ChangeResult<T> is a union, the feature new in C# 15 with .NET 11: the compiler knows every case it can hold. .ToHttp() is this switch, written for you.

Write your own when an endpoint needs something different. There is no default arm, so leaving a case out stops the build.

public static IResult ToHttp<T>(this ChangeResult<T> outcome) where T : notnull => outcome switch
{
    T x => Results.Ok(x),
    Missing x => Results.NotFound(x),
    Refused x => Results.UnprocessableEntity(x),
    Stale x => Results.Conflict(x),
    Invalid x => Results.BadRequest(x),

What the data layer buys you

  • A state that should not exist cannot be written. Equipment is available, or out of service with a reason; never half of each.
  • A value that passed validation stays valid, and one kind of id cannot be passed as another.
  • Every expected failure reaches your endpoint as a named case you must handle: not found, refused by a rule, changed by someone else, invalid.
  • Two people editing the same record cannot silently overwrite each other.
  • Every query is checked against the real schema when the application starts.
  • The whole application publishes as one native binary, with no warnings from Plasm.

Six things it won't do behind your back

Each one is an executable Gherkin scenario, run against a real PostgreSQL database.

No hidden database access

What a record owns or links is read with it, as a plain field. Nothing is loaded lazily, and nothing is left unloaded.

Nothing runs client-side by accident

A predicate that cannot be translated fails with the expression named.

No N+1, no cartesian products

Each owned or linked list is one command per batch of owner keys, however many owners are read.

Partial data cannot destroy data

An update writes only the columns that differ. A projection is not a record and cannot be written back.

Concurrency is checked

By a version field, or by every column of the record the change was made from, in the same command.

Problems surface at start-up

Starting a repository translates every query value and compares the model with the database, naming each problem.

Writes are transactions
transaction {
    let! order = Tx.oneAsSeen (orderById id, seen) |> Tx.orReject (Missing "order")
    let! changed = decide order |> Tx.ofResult Domain
    return! Tx.update (order, changed)
}
