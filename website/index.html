Ecto's design · expressed in F#

Persistence that thinks in F#.

Your domain's own immutable records, stored as they are, with what they own. Compiler-checked queries and typed transactions are values; the repo is the only place anything touches the database. There is one way to build an application with it.

Get started See examples 
let page customer =
    plasm {
        for o in tableOf<Order> do
            where (o.CustomerId = Some customer)
            orderByDescending o.PlacedAt
            take 20
    }

let! orders = repo.All(page customerId)
// Result<Order list, DbError>: every Order with its Lines

Six things it won't do behind your back

Each one is an executable Gherkin scenario, run against a real PostgreSQL database.

No hidden database access

What a record owns or links is read with it, as a plain list. Reading a field never queries, and an empty list always means empty.

Nothing runs client-side by accident

A predicate that can't become SQL fails with the expression named. Rows are never fetched to be filtered in memory.

No N+1, no cartesian product

Each owned or linked list is one command per batch of owner keys. Sibling lists are read separately.

Your rules, not Plasm's

Plasm validates no input. Your constructors and functions decide, and a transaction's refusals are of your own error type.

Typed throughout

Comparing o.Total with a string, or mixing OrderId with CustomerId, won't compile. Stored values are read through your types' own create.

Only what changed is written

An update writes the columns that differ from the record read, and owned lists by difference, under an optimistic version check.

How a page of orders loads

The orders are chosen first. Their lines then receive exactly the selected keys as one array parameter. Payments are another aggregate, so the application reads them by a second query, for the same keys.

  1. 1 · the ordersordersORDER BY placed_at DESC, id LIMIT 20
  2. 2 · what they ownorder_linesorder_id = ANY(@keys)
  3. 3 · another aggregate, by idpaymentsorder_id = ANY(@keys) AND status = @p1

You can inspect any plan without touching the database: repo.Explain query returns the SQL and the lists read with it.

Your domain decides

The rules are plain functions over your records, with no persistence in them. Plasm stores the record they return, and validates nothing itself.

let cancel (reason: string) (order: Order) =
    match order.Status with
    | Cancelled _ -> Error AlreadyCancelled
    | _ when String.IsNullOrWhiteSpace reason -> Error ReasonRequired
    | _ -> Ok { order with Status = Cancelled(reason.Trim()) }

// A constraint with PostgreSQL's default name is the field's error:
// customers_email_key -> { Field = "Email"; Kind = UniqueConstraint ... }

Writes are transactions

Every write is a typed transaction. Steps pass results with let!; a failure says where its step is written and what was rolled back, and a refusal has your own error type. Retries are opt-in.

let cancelOrder id seen reason : Tx<Order, Refusal> =
    transaction {
        let! order = Tx.one (orderById id) |> Tx.orReject (Missing "order")
        let! changed = cancel reason order |> Tx.ofResult Domain
        return! Tx.update (order, changed, expectVersion = seen)
    }

match! repo.Transact(cancelOrder id version "changed my mind") with
| Ok order -> ...
| Error { Failure = TxFailure.Rejected r } -> ...   // your Refusal
| Error { Failure = TxFailure.Conflict _ } -> ...   // a newer version is stored
| Error e -> printfn "%O failed; rolled back %A" e.Step e.RolledBack

Plasm sends as few commands as EF split query and reads the same rows, but it is slower and allocates more, because the scalars it reads by convention are converted by reflection on every row. With the same model and registered mappings, a page of 1,000 measured 23 ms and 20 MB, level with EF split query on time; that conversion is the next thing to fix. These were measured on one machine, shared with other work, against a local database; the full method and limitations are in docs/benchmarks.md.

Honest status

An experimental first delivery, not production-ready. Ecto's design transfers; its operational maturity has to be earned.

Every behaviour is an executable Gherkin scenario, run against PostgreSQL

Works today

  • Your own records as the model, with attributes for the table and what types can't say; scalars by convention
  • Owned lists and records, linked lists, unions with fields
  • Typed queries, projections, exists across aggregates
  • Inner and left joins, with option-typed left sides
  • Typed transactions, constraints as field errors, optimistic concurrency
  • Count, exists, aggregates, group by and having
  • Bulk update, delete, insert and upsert
  • Typed hand-written SQL; prepared queries
  • Printed DDL; schema and query checks; test sandboxes
  • F# Interactive: query displays, playground, scaffolding

Not yet

  • Right and full joins, unions, CTEs
  • Composite keys, JSON columns
  • Prepared projections; published packages
  • Databases other than PostgreSQL
