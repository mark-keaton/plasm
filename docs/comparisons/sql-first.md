## Facil (cmeeren/Facil)

Facil generates F# source from SQL scripts, stored procedures and per-table CRUD templates at build time, by connecting to a database. The generated file is checked in. **SQL Server only** ("Supports SQL Server 2012 and up"; 3.1.0 added SQL Server 2025 syntax). Runtime package targets .NET Standard 2.0 and depends on `Microsoft.Data.SqlClient >= 5.2.2` and `Microsoft.SqlServer.Types`. Since 3.0.0 the generator needs the .NET 10 SDK at build time. Source: README, RELEASE_NOTES.md, nuspec.

1. **Enums and unions.** Not applicable in the PostgreSQL sense: SQL Server has no enum types, and Facil has no PostgreSQL support, so `MapEnum` and the Npgsql 7/8 type-mapping changes are irrelevant to it. Facil produces DTO records (anonymous records, generated table DTOs or "any record type you specify that is constructible by the generated code"). Unions are not generated or mapped; you convert DTOs to domain types yourself (Fling's design assumes `toDomain`/`toDto` functions). The README contrasts itself with type providers, which cannot provide union types; Facil's generated code is plain records.
2. **Options and nulls.** Nullable output columns become `option`, or `voption` if configured (separately for inputs and outputs, per script, procedure or table DTO). Stored-procedure parameters with a `NULL` default become optional. Script parameter nullability **is not inferred** (SQL Server's `sp_describe_undeclared_parameters` limitation): Facil assumes non-null unless you override it in YAML. Since 2.11.0 you can override column nullability for cases SQL Server infers wrongly (e.g. `COALESCE`). Source: README "Type inference limitations in scripts", "How are default and nullable parameter values handled?".
3. **Relationships and loading.** None in Facil itself: one script or procedure per call, results as `ResizeArray`. The generated CRUD templates include "get rows by a batch of primary keys (using a TVP)" and "get rows by a batch of arbitrary columns", which are the building blocks for N+1-free loading. The companion library **Fling** composes them: `createBatchLoader ... |> batchLoadChildren Db.getOrderLinesForOrders _.OrderId |> batchLoadOptChild ...` does "at most one fetch per Db function" for a batch of parents, which is the same shape as Plasm's `preload` (one command per relationship per batch). You write that composition by hand per aggregate; there is no query language for filtering or ordering children. Multiple result sets: not documented as a feature; a raw `SqlDataReader` API exists for custom mapping **[unverified whether multiple result sets are generated]**. Issue #71 (2026-07-01, open) asks about MARS.
4. **Writes and transactions.** Generated per-table insert/update/MERGE-upsert/delete and **batch** insert/update/upsert/delete (TVP-based, with output columns), plus your own procedures. Transactions are ADO.NET: pass an open `SqlConnection` and `SqlTransaction` to `WithConnection(conn, tran)`; you commit. Fling adds change-aware aggregate saves ("only inserts/updates/deletes changed rows" by diffing old and new aggregate). No validation layer.
5. **Compile-time checking.** The strongest of the three: generated types come from the real database, so a column rename or type change breaks compilation after regeneration. Regeneration happens only when config, scripts or Facil change, or `FACIL_FORCE_REGENERATE` is set; it **does not pick up database changes on its own** (by design). CI: because the output is checked in, CI needs no database. `FACIL_FAIL_ON_REGENERATE` (2.15.1, 2026-01-31) fails the build if regeneration would be triggered, without needing connection strings; `FACIL_FAIL_ON_CHANGED_OUTPUT` needs the database. Build-time query execution (for dynamic SQL result sets) runs in a rolled-back transaction. Source: README FAQ.
6. **Errors.** Exceptions (SqlClient's). Generated methods return values (`option` for single rows, `ResizeArray` otherwise) and throw on database failure; no `Result`. **[inferred from README examples; no classification layer is described]**
7. **Database support.** SQL Server only.
8. **Maintenance.** Active: four minor/major releases in 2026, last commit 2026-11-04, 4 open issues. Single maintainer ("limited capacity for open-source maintenance"; feature additions are conservative). README states it is production ready, "over 2000 tests", "used in several mission-critical production services at our company". 3.3.0 ships an agent skill in the package.
9. **Developer experience.** Fluent API (`GetUserById.WithConnection(connStr).WithParameters(userId).AsyncExecuteSingle()`), DTO-as-parameters overloads, lazy `seq`/`IAsyncEnumerable` execution, TVPs, temp tables via `SqlBulkCopy`. Cost: YAML configuration, a development database reachable at generation time, and a large generated file in the repo.

## Npgsql.FSharp (Zaid-Ajaj/Npgsql.FSharp)

A thin functional pipeline over Npgsql: `Sql.connect |> Sql.query "..." |> Sql.parameters [ "name", Sql.text v ] |> Sql.execute (fun read -> ...)`, with hand-written row readers. Version 8.0.0 targets net8.0 and depends on `Npgsql >= 8.0.6`, `FSharp.Core >= 9.0.100`. Source: README, `src/Npgsql.FSharp.fs`, `src/Common.fs`, nuspec.

1. **Enums and unions.** No enum support in the library: `SqlValue` has no enum case (`Common.fs`). Issue #144 "Enum Support" (2023-11-30) asks for PostgreSQL enums mapped to F# unions and is **open with no resolution**. Workarounds: pass `Sql.parameter (NpgsqlParameter(..., DataTypeName = "mood"))` or cast in SQL (`@status::mood`), and read with `read.text` then map to the union yourself. Npgsql 7 made `NpgsqlDataSource` "the recommended way to manage type mapping" and made `NpgsqlConnection.GlobalTypeMapper` obsolete (still supported), removing per-connection `conn.TypeMapper.MapEnum` (npgsql.org, "Enums and composites"). Npgsql.FSharp accepts a data source (`Sql.fromDataSource`, added with .NET 7 support), so you can build one with `NpgsqlDataSourceBuilder.MapEnum<MyClrEnum>()` and read via `read.fieldValue<MyClrEnum>`. `MapEnum` needs a CLR `enum`, not an F# union, so union mapping is still manual. Unmapped enums can be read and written as strings (`GetFieldValue<string>`; write with `DataTypeName` set) per the Npgsql docs.
2. **Options and nulls.** Explicit and good: `read.textOrNone`, `intOrNone`, etc. (plus `...OrValueNone` for `voption`), and `Sql.textOrNone` etc. for parameters. Reading a nullable column with the non-option reader throws. The analyzer flags nullable columns read with non-option readers.
3. **Relationships and loading.** Hand-written joins mapped row by row, or several queries you combine yourself. Multiple result sets from one command are **not supported**: issue #83 (opened 2021-01-20) is still open. N+1 avoidance is up to you (e.g. `WHERE order_id = ANY(@ids)` with `Sql.intArray`, then group in F#). No relationship model.
4. **Writes and transactions.** `Sql.executeNonQuery` (affected rows); `Sql.executeTransaction [ query, [paramSet1; paramSet2] ]` runs each query for each parameter set in one transaction using `NpgsqlBatch` (one round trip per query group) and returns affected rows per query. It cannot use intermediate results; for that, create an `NpgsqlTransaction` yourself and use `Sql.existingConnection`/`Sql.transaction` (README "Executing SQL commands in the context of a transaction"). No upsert or bulk helpers beyond the batch.
5. **Compile-time checking** — see the analyzer below. The library itself checks nothing.
6. **Errors.** Exceptions. The source throws `MissingQueryException`, `NoResultsException` (from `executeRow` on no rows), `UnknownColumnException`, and Npgsql's `PostgresException`. The README still says `executeNonQuery` "returns `Result<int, exn>`", but the current source returns `int` (`let executeNonQuery (props: SqlProps) : int`), so that README line is stale.
7. **Database support.** PostgreSQL only.
8. **Maintenance.** Quiet. Last release 8.0.0 on 2024-12-07 (by a co-maintainer: net8 update, Testcontainers, jsonb fix). Before that, 5.7.0 on 2023-04-06. Since then only a dependabot merge in `/docs` (2025-07-18). 16 open issues and PRs, the newest from 2023. It is the most downloaded library here (~7.6M on NuGet) and is used in SAFE-stack-style apps **[usage claim unverified beyond the download count]**. It works with Npgsql 8; its open dependency range means it restores against Npgsql 9/10, but **[unverified]** whether it is tested there.
9. **Developer experience.** Very little to learn; SQL is plain strings; readers are explicit. Parameter names are strings that must match the SQL (the analyzer's main value is catching mismatches). Plain `Sql.query (sprintf ...)` also compiles, so nothing prevents splicing values into SQL text.

### Npgsql.FSharp.Analyzer (Zaid-Ajaj/Npgsql.FSharp.Analyzer, package `NpgsqlFSharpAnalyzer`)

An F# analyzer that, at design time, connects to a development database (connection string from a `NPGSQL_FSHARP` file or env var), checks query syntax, missing or redundant parameters, parameter types, the columns and types read in `Sql.execute` lambdas, and nullable columns read as non-options. It has code fixes and a `Sql.skipAnalysis` escape. Queries must be inline literals or `[<Literal>]` strings in the same module (or loaded via FSharp.Data.LiteralProviders). It runs in Ionide (via the F# Analyzers SDK), Visual Studio (a VSIX from releases) and the CLI (`ubik`).

- **Builds and CI:** the analyzer needs a live database with the current schema wherever it runs. In CI that means starting PostgreSQL, applying migrations and running `ubik`. It does not run as part of `dotnet build`.
- **Maintenance: effectively dormant.** The last release, 3.26.1, was on 2021-05-06; the last commit on 2021-08-09. The package targets `net5.0` and depends on `FSharp.Analyzers.SDK 0.8.0`. Current Ionide and the `fsharp-analyzers` CLI load only analyzers built against the matching, much newer SDK, so **[unverified, but likely]** the analyzer will not load in a current toolchain without a rebuild. `ubik` may still work as a standalone tool **[unverified]**. Whether it understands Npgsql.FSharp 8's API or PostgreSQL enum columns is also **[unverified]**.

## Donald (pimbrouwers/Donald)

A generic ADO.NET wrapper for any provider: `conn |> Db.newCommand sql |> Db.setParams [ "id", SqlType.Int32 1 ] |> Db.query (fun rd -> ...)`. Version 10.1.0 targets net6/7/8 and depends only on FSharp.Core. Source: README, `src/Donald/Db.fs`, `src/Donald/IDataReader.fs`.

1. **Enums and unions.** Nothing built in. `SqlType` covers primitives only (String, Int32, Guid, DateTime, Bytes...). Issue #55 (2024-05-08, open) asks for `DateOnly`/`TimeOnly`. For PostgreSQL enums, use `Db.setParamsRaw [ "s", box (NpgsqlParameter(..., DataTypeName = "mood")) ]` or a SQL cast, read with `ReadString`, and map yourself. Because Donald takes any `IDbConnection`, connections from an `NpgsqlDataSource` with `MapEnum` work, but the reader extensions have no enum helpers **[inferred]**.
2. **Options and nulls.** `rd.ReadStringOption` etc. return options. The non-option readers **silently default on NULL**: `ReadString` returns `String.Empty`, `ReadBoolean` returns `false`, `ReadByte` returns `Byte.MinValue`, and so on (`IDataReader.fs`). That can hide nulls the type should have made visible.
3. **Relationships and loading.** Hand-written joins; `Db.read` exposes the raw `IDataReader`, so multiple result sets are possible with manual `NextResult()` **[inferred from `Db.read` source]**. An open PR (#50, 2022-11-26) adds a docs example of a join with `Db.read`. Nothing prevents N+1.
4. **Writes and transactions.** `Db.exec`, `Db.execMany` (one command per parameter set), and `Db.batch (fun tran -> ...)`, which commits on success and rolls back on any exception. There are also `TryBeginTransaction`/`TryCommit`/`TryRollback` extensions.
5. **Compile-time checking.** None.
6. **Errors.** Exceptions with context: `DbConnectionException`, `DbExecutionException` (statement and transaction step), `DbReaderException` (field name), `DbTransactionException`. Older versions returned values (`DbResult<'a> = Result<'a, DbException>` in v4.0.0, 2020-11-16); the current API throws.
7. **Database support.** Any ADO.NET provider (SQL Server, SQLite, MySQL, PostgreSQL...).
8. **Maintenance.** Quiet. Last release 10.1.0 on 2024-03-20; last code commit 2024-04-02; README edits 2024-12-02. 2 open issues and a handful of stale dependabot PRs (2023). Small API, so "finished" is plausible, but there is no .NET 9/10 target (net8.0 assets load on later runtimes).
9. **Developer experience.** Minimal and predictable. `CommandBehavior.SequentialAccess` is on by default, so **columns must be read in SELECT order**, a constraint that comes up when hand-mapping joins.

## What these do that Plasm does not

- **Design-time or build-time checking of SQL against the real schema.** Facil (generation from the live database, checked-in output, CI without a database via `FACIL_FAIL_ON_REGENERATE`) and the Npgsql.FSharp analyzer (when it still loads) catch wrong columns, types and nullability before running. Plasm checks its typed queries against the F# model at compile time. Its link to the database is `repo.CheckSchema()`, at run time, and only for mapped schemas. **Plasm's `repo.Sql` text is not checked at all** until it runs. A missing column becomes a materialisation error naming the field, which is good, but it only appears at run time.
- **SQL as the source of truth.** Facil consumes existing stored procedures, scripts, TVPs and temp tables. Plasm has no stored-procedure support (no output parameters or return values), and its SQL escape hatch is inline interpolated strings, not `.sql` files.
- **Streaming large results.** Facil (lazy `seq`/`IAsyncEnumerable`), Npgsql.FSharp (`Sql.iter`, `Sql.toSeq`) and Donald (`Db.read` with `SequentialAccess`) can stream. Plasm returns lists; streaming is listed as not built (`docs/status.md` gaps).
- **Raw reader access, and with it multiple result sets** (Donald's `Db.read`, Facil's reader API). Plasm's `repo.Sql` maps exactly one result set to `'R list`. `Tx.run` gives a `TxContext.CreateCommand()` for arbitrary ADO.NET inside a transaction, but that is a lower-level escape.
- **Other databases.** Donald works with any ADO.NET provider; Facil covers SQL Server deeply (hierarchyid, geometry, TVPs). Plasm is PostgreSQL only.
- **Change-aware aggregate saves without a changeset** (Fling diffs the old and new aggregate and writes only changed child rows). Plasm needs explicit changesets, `putChildren` or `replaceChildren` with a scope and removal policy. That is more explicit and safer, but more ceremony.
- **Maturity and production use.** Facil is in production and recently released. Npgsql.FSharp has millions of downloads. Plasm has no production use and no published package.
- **Very small conceptual surface** (Npgsql.FSharp, Donald). There is no model, schema DSL or quotation translation to learn, and no build/plan cost per query (Plasm's measured ~80 µs build plus ~60 µs plan for an unprepared query).

## What Plasm does that these do not

- **Relationship loading as a query feature.** `preload o.Lines (child query)` with filtering, ordering, `limitPerParent` and nesting, one `= ANY(@keys)` command per relationship per batch, with no cartesian product and identity-shared targets. None of the three has a relationship model. The closest is Facil + Fling, which batch-loads children with hand-written per-relationship functions and offers no child filters or per-parent limits. With Npgsql.FSharp or Donald you write the `ANY(@ids)` query and the grouping yourself every time. `Assoc<'T> = NotLoaded | Loaded` makes "not loaded" visible in the type, and no library here tracks that.
- **F# unions as stored values, by design.** `Scalar.enum [ Pending, "pending"; ... ]` maps a fieldless union to text with every case required, and unknown stored text becomes a materialisation error. `Scalar.wrap`/`tryWrap` map single-case and validated domain types. All three libraries leave union and domain-type mapping to hand-written readers (Npgsql.FSharp issue #144, open since 2023).
  - **Caveat, a gap shared with the others:** `Scalar.enum` sends a **`text`** parameter (`ProviderType = typeof<string>`; `Execution.fs` sets `p.Value` with no `DataTypeName`). Against a native PostgreSQL `CREATE TYPE ... AS ENUM` column, inserts and `WHERE status = @p` would therefore fail with "column is of type X but expression is of type text". `CheckSchema` would also flag such a column, because `ColumnTypes typeof<string>` lists only text-like types. **[inferred from code; not run]** `PostgresProvider` does accept an `NpgsqlDataSource`, so a `MapEnum`'d data source can be supplied, but Plasm has no way to map an F# union to a PostgreSQL enum type. This is a candidate feature file.
- **Injection-safe hand-written SQL by construction.** `repo.Sql`/`ExecuteSql`/`Tx.sql` take a `FormattableString`, so every hole becomes a parameter (including options, domain scalars and lists as one array parameter), and a plain `string` does not type-check. `Raw.fragment` must be a literal format string. Npgsql.FSharp and Donald accept any string, so `sprintf` splicing compiles. Facil avoids the problem by using scripts. Plasm's raw SQL also needs **no parameter names, no `SqlType`/`Sql.int` tags and no reader lambdas**: results map by name to mapped records (relationships `NotLoaded`, and then `repo.Preload` can load them onto those rows), to unmapped records (by name or snake_case), to tuples (in order) or to scalars, with numeric conversion.
- **What Plasm's raw SQL lacks compared with them:** no check against the database before run time (Facil, the analyzer); no streaming or raw-reader access; one result set only; no stored-procedure output parameters; no batching of one statement over many parameter sets (Npgsql.FSharp `executeTransaction` with `NpgsqlBatch`, Donald `execMany`), though `Bulk.insert`/`upsert` cover the set-based write case for mapped records; no `.sql` file sources or shared fragments (Facil 3.2 `{{include}}`); and no per-parameter type override (e.g. `DataTypeName`) for exotic PostgreSQL types such as enums, `jsonb` or `pgvector` **[inferred: interpolated values go through the model's scalar mappings, and no override is documented]**.
- **Errors as values with classification.** Repository calls return `Result` with `WriteError.Invalid`/`Stale`/`Failed` and `DbError`, and classify failures (`DbFailureKind.UniqueViolation`, foreign key, check, timeout, serialisation, SQLSTATE and constraint name). Constraint mapping can turn violations into changeset field errors. All three libraries throw. Donald adds context to its exceptions; Npgsql.FSharp's README still claims `Result` but the code throws.
- **Transactions as values.** `transaction { }` with typed steps found by where they are written, a typed rejection (`Tx<'T, 'E>`), isolation levels, opt-in retry on serialisation failure, and `Tx.sql` inside. The others offer an all-or-nothing callback (Donald `Db.batch`), a fixed list of statements (Npgsql.FSharp `executeTransaction`) or raw ADO.NET transactions.
- **Typed composable queries, aggregates and bulk writes** without writing SQL: joins with option semantics for left joins, `Agg.*`, `Bulk.update` via copy-and-update, upserts, and prepared queries. Facil's CRUD templates are the nearest equivalent and cover only per-table key and column lookups.
- **Changesets and validation.** Validation is pure and per field, and unmentioned fields are never written. Nothing comparable exists in the three; Fling diffs aggregates but does no validation.
- **Testing and exploration support.** `repo.Sandbox` gives rolled-back test transactions with savepoints, FSI query display with SQL and parameters, `repo.Playground`, and `repo.Scaffold`. None of the three has these. Facil's build-time execution uses a rolled-back transaction, but only for generation.

### Takeaways for Plasm (candidate feature files)

1. Native PostgreSQL enum columns: `Scalar.pgEnum "order_status" [ ... ]`, sending `DataTypeName` and accepting `USER-DEFINED` in `CheckSchema`. No library here does this for F# unions.
2. An optional check of `repo.Sql` text: a `CheckSchema`-time or test-time "describe" of registered raw queries against the live database (PostgreSQL can describe a prepared statement without running it). That would close most of the gap with Facil and the analyzer without code generation.
3. Streaming (`IAsyncEnumerable`) for `repo.Sql` and `repo.All` without preloads.
4. A per-hole type override in interpolated SQL (e.g. `{Sql.typed "jsonb" v}`) for PostgreSQL types the model does not map.
